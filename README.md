# Customer Ops

An internal operations console for a customer-support team — a CRM, a multi-channel ticket queue, an escalation approval workflow, and a PDF-backed knowledge base — with an AI "Agent Assist" chatbot layered on top that looks up records, answers policy questions with real citations, and proposes account/ticket changes for a human to confirm before anything actually writes to the database.

Built as two independently runnable halves in one repo: a FastAPI backend and a React frontend.

## Key Features

**Operations console**
- Customer CRM — search, profile, order history, ticket history, internal notes
- Ticket Queue — a kanban board pre-grouped by channel (email/chat/phone/social) × status
- Escalation Queue — a team-lead-only approval workflow for refunds, SLA exceptions, account credits, and retention overrides
- Knowledge Base — PDF upload, versioning, category tagging, and direct semantic search, with duplicate-content detection
- Agent Directory — roster with team/on-duty filtering
- Data Sources — mock integration cards (Zendesk, Salesforce, Shopify, Slack) with a "Sync Now" action
- Activity Log — a full audit trail of every write the system has made, chat-driven or manual
- Analytics Dashboard — ticket volume, resolution time, CSAT, and AI deflection rate, backed by real SQL aggregation

**AI Agent Assist**
- One chat endpoint routed by an LLM classifier into seven capabilities: CRM lookup, CRM field edits, queue availability, policy Q&A, escalation filing, reporting, and greetings
- Grounded, cited policy answers — the model only ever sees retrieved knowledge-base passages, and citations are built from retrieval metadata, never generated by the model itself
- Every write (a field edit, a ticket reassignment, a scheduled callback, a new escalation) is **proposed first** and only executes after a human clicks Confirm — nothing lands on the LLM's own turn
- LLM-generated SQL for lookups is independently re-parsed and validated against a table allow-list before it ever touches the database
- Chat replies render real markdown — bold, italic, underline, inline code, bullet and numbered lists — instead of a raw text dump
- Automatic retries, a circuit breaker, and graceful degradation if the LLM is unavailable or rate-limited

## Tech Stack

**Backend** — FastAPI · SQLAlchemy 2.0 · SQLite · Google ADK + Gemini 2.0 Flash (LLM orchestration) · ChromaDB (RAG vector store) · `sqlglot` (SQL safety gate) · `pyjwt` / `bcrypt` (auth) · `uv` (packaging) · Python ≥3.12

**Frontend** — React 19 · TypeScript · Vite 8 · Tailwind CSS v4 · React Router v7 · Recharts · lucide-react

## Architecture at a Glance

```
┌─────────────────────────┐        HTTPS / JSON          ┌──────────────────────────────┐
│   React SPA (frontend)  │ ────────────────────────────▶│    FastAPI backend           │
│   localhost:5173        │◀──────────────────────────── │    localhost:8000            │
└─────────────────────────┘        Bearer JWT             └───────────────┬───────────────┘
                                                                           │
                                        ┌──────────────────────────────────┼──────────────────────────────┐
                                        │                                  │                              │
                                 SQLite (customer_ops.db)          ChromaDB (data/chroma)            Google Gemini
                                 all CRUD data                     vector store for KB PDFs      one router + five sub-agents
```

A single monolithic FastAPI process talking to a local SQLite file and a local ChromaDB folder — no separate services, no message queue. The one non-CRUD capability, the AI Agent Assist, is a router agent plus five specialist sub-agents (CRM, queue/availability, policy RAG, escalation, and the deterministic read/analytics paths), each a structured, retry-and-circuit-breaker-wrapped call to Gemini.

## Getting Started

**Prerequisites:** Python ≥3.12 with [`uv`](https://docs.astral.sh/uv/) installed, Node.js ≥18, and (optionally) a free [Gemini API key](https://aistudio.google.com/app/apikey).

### 1. Backend

```bash
cd backend
uv sync
cp .env.example .env
```

Edit `.env` and set:
- `GEMINI_API_KEY` — from the link above. **No key?** Set `DEMO_MODE=true` instead — the app still boots and every screen works; chat replies just always return a clean "temporarily unavailable" message rather than the app failing to start.
- `JWT_SECRET_KEY` — generate one: `python -c "import secrets; print(secrets.token_urlsafe(48))"`

Seed the database (drops and recreates everything — customers, orders, tickets, agents, escalations, KB documents, mock data sources):

```bash
uv run python -m data.seed_data
```

Run it:

```bash
uv run uvicorn app.main:app --reload
```

Backend is now live at `http://localhost:8000` (Swagger UI at `/docs`).

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Frontend is now live at `http://localhost:5173`, talking to the backend at `http://localhost:8000/api/v1` by default (override with `VITE_API_BASE_URL` in `frontend/.env` if needed).

Open `http://localhost:5173` and sign in with one of the demo accounts below.

## Environment Variables

Full reference lives in `backend/.env.example`. The ones you actually need to touch for local dev:

| Variable | Where | Purpose |
|---|---|---|
| `GEMINI_API_KEY` | `backend/.env` | powers the AI Agent Assist. Omit + set `DEMO_MODE=true` to run without one |
| `JWT_SECRET_KEY` | `backend/.env` | signs login tokens and chat action-confirmation tokens |
| `DATABASE_URL` | `backend/.env` | defaults to a local SQLite file, `sqlite:///./customer_ops.db` |
| `VITE_API_BASE_URL` | `frontend/.env` | defaults to `http://localhost:8000/api/v1` |

## Trying the AI Chat Assistant

Open the chat FAB (bottom-right, on any page once logged in) and try:

- `list all customers` — a CRM lookup, rendered as a formatted bullet list
- `find customer Daniel Brooks`, then, while on their profile: `change her phone to +1-555-9999` — proposes a field edit; click **Authorize Action** to confirm it
- `what's our refund policy for orders over 30 days old?` — a cited policy answer pulled from the seeded knowledge base
- `how many agents are online right now` — live queue availability
- `issue a $10 account credit for a shipping delay` — small amounts auto-approve on creation; try a larger amount to see it land in the Escalation Queue instead (team-lead login required to approve/reject it there)

## Testing

```bash
cd backend
uv run pytest
```

Runs fully offline — no Gemini key or network access needed. The suite covers deterministic logic only (SQL-security allow-list, entity resolution, circuit breaker, CRUD, the signed-token propose→confirm flow, analytics aggregation), never live LLM classification. Each run gets its own throwaway SQLite DB and Chroma directory — your real `customer_ops.db` is never touched.

The frontend has no automated test suite; `npm run build` (which runs `tsc -b` first) is the closest thing to a regression check.

## Deployment

- **Backend** — `backend/requirements.txt` is a pinned, production-only export of the `uv` lockfile, ready for a standard Python host (e.g. Render): start command `uvicorn app.main:app --host 0.0.0.0 --port $PORT`, set `GEMINI_API_KEY`, `JWT_SECRET_KEY`, `DEBUG=false`, and `CORS_ORIGINS` to your deployed frontend's URL as environment variables. Note SQLite and the Chroma vector store both live on local disk — attach persistent storage (or re-seed after every deploy) if the host's filesystem is ephemeral.
- **Frontend** — a standard static Vite build (`npm run build` → `dist/`), deployable to any static host (Vercel, Netlify, etc.); set `VITE_API_BASE_URL` to the deployed backend's URL at build time.
