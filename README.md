# Customer Ops

An internal operations console for a customer-support team — a CRM, a multi-channel ticket queue, an escalation approval workflow, and a PDF-backed knowledge base — with an AI "Agent Assist" chatbot layered on top that looks up records, answers policy questions with real citations, and proposes account/ticket changes for a human to confirm before anything actually writes to the database.

Built as two independently runnable halves in one repo: a FastAPI backend and a React frontend.

## Key Features

**Operations console**
- Customer CRM — search, profile, order history, ticket history, internal notes
- Ticket Queue — a kanban board pre-grouped by channel (email/chat/phone/social) × status
- Escalation Queue — a team-lead-only approval workflow for refunds, SLA exceptions, account credits, and retention overrides
- Knowledge Base — PDF upload, versioning, category tagging, and direct semantic search, with duplicate-content detection
- Agent Directory — roster with team/on-duty filtering
- Data Sources — mock integration cards (Zendesk, Salesforce, Shopify, Slack) with a "Sync Now" action
- Activity Log — a full audit trail of every write the system has made, chat-driven or manual
- Analytics Dashboard — ticket volume, resolution time, CSAT, and AI deflection rate, backed by real SQL aggregation

**AI Agent Assist**
- A single unified agent with real tool-calling (Google ADK function-calling, not a hand-rolled classifier) decides itself which of ten tools to call — customer/ticket/order lookup, queue availability, policy search, reporting, or one of five propose-only write actions — instead of routing through a fixed category list
- Real multi-turn memory — every chat session is persisted (last 10 turns fed back to the model on each request), so a follow-up like "for ticket X, $1000" after "I want to raise an escalation" is understood in context, not treated as a fresh, isolated message
- Grounded, cited policy answers — the model only ever sees retrieved knowledge-base passages, and citations are built from retrieval metadata, never generated by the model itself
- Every write (a field edit, a ticket reassignment, a scheduled callback, a new escalation, **or a new ticket**) is **proposed first** and only executes after a human clicks Confirm — nothing lands on the LLM's own turn, and a tool that doesn't have enough to go on asks a clarifying question instead of guessing
- Filing or resolving an escalation writes a visible entry to the ticket's own event timeline, not just the global audit log — anyone opening the ticket can see whether an escalation was ever filed and whether it was approved or rejected
- LLM-generated SQL for lookups is independently re-parsed and validated against a table allow-list before it ever touches the database
- Chat replies render real markdown — bold, italic, underline, inline code, bullet and numbered lists — instead of a raw text dump
- Automatic retries, a circuit breaker, and graceful degradation if the LLM is unavailable or rate-limited

## Tech Stack

**Backend** — FastAPI · SQLAlchemy 2.0 · SQLite locally / Postgres-ready for deployment (`psycopg2-binary`) · Google ADK + Gemini (tool-calling agent) · ChromaDB (RAG vector store) · `sqlglot` (SQL safety gate) · `pyjwt` / `bcrypt` (auth) · `uv` (packaging) · Python ≥3.12

**Frontend** — React 19 · TypeScript · Vite 8 · Tailwind CSS v4 · React Router v7 · Recharts · lucide-react

## Architecture at a Glance

```
┌─────────────────────────┐        HTTPS / JSON          ┌──────────────────────────────┐
│   React SPA (frontend)  │ ────────────────────────────▶│    FastAPI backend           │
│   localhost:5173        │◀──────────────────────────── │    localhost:8000            │
└─────────────────────────┘        Bearer JWT             └───────────────┬───────────────┘
                                                                           │
                          ┌────────────────────────────────────────────────┼──────────────────────────────┐
                          │                                                │                              │
                   SQLite / Postgres                                ChromaDB (data/chroma)            Google Gemini
             all CRUD data + chat session history          vector store for KB PDFs, rebuilt      one unified agent, 10 tools
                                                             from the DB on boot if empty        (ADK function-calling, not a router)
```

A single monolithic FastAPI process talking to a SQL database and a local ChromaDB folder — no separate services, no message queue. The one non-CRUD capability, the AI Agent Assist, is a single agent (`ops_agent`) with real tool-calling: the model itself decides which of ten tools to call (grouped as read-only lookups, one policy-search tool, and five propose-only writes) based on the message plus up to 10 turns of persisted conversation history, instead of a fixed classify-then-dispatch step. Every LLM call is retry-and-circuit-breaker-wrapped.

## Getting Started

**Prerequisites:** Python ≥3.12 with [`uv`](https://docs.astral.sh/uv/) installed, Node.js ≥18, and (optionally) a free [Gemini API key](https://aistudio.google.com/app/apikey).

### 1. Backend

```bash
cd backend
uv sync
cp .env.example .env
```

Edit `.env` and set:
- `GEMINI_API_KEY` — from the link above. **No key?** Set `DEMO_MODE=true` instead — the app still boots and every screen works; chat replies just always return a clean "temporarily unavailable" message rather than the app failing to start.
- `JWT_SECRET_KEY` — generate one: `python -c "import secrets; print(secrets.token_urlsafe(48))"`

Seed the database (drops and recreates everything — customers, orders, tickets, agents, escalations, KB documents, mock data sources):

```bash
uv run python -m data.seed_data
```

Run it:

```bash
uv run uvicorn app.main:app --reload
```

Backend is now live at `http://localhost:8000` (Swagger UI at `/docs`).

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Frontend is now live at `http://localhost:5173`, talking to the backend at `http://localhost:8000/api/v1` by default (override with `VITE_API_BASE_URL` in `frontend/.env` if needed).

Open `http://localhost:5173` and sign in with one of the demo accounts below.

## Environment Variables

Full reference lives in `backend/.env.example`. The ones you actually need to touch for local dev:

| Variable | Where | Purpose |
|---|---|---|
| `GEMINI_API_KEY` | `backend/.env` | powers the AI Agent Assist. Omit + set `DEMO_MODE=true` to run without one |
| `JWT_SECRET_KEY` | `backend/.env` | signs login tokens and chat action-confirmation tokens |
| `DATABASE_URL` | `backend/.env` | defaults to a local SQLite file, `sqlite:///./customer_ops.db`; point it at a Postgres connection string (e.g. Neon) for deployment — the app runs unmodified against either |
| `VITE_API_BASE_URL` | `frontend/.env` | defaults to `http://localhost:8000/api/v1` |

## Trying the AI Chat Assistant

Open the chat FAB (bottom-right, on any page once logged in) and try:

- `list all customers` — a CRM lookup, rendered as a formatted bullet list
- `find Daniel Brooks and change his phone to +1-555-9999` — resolves the customer by name and proposes a field edit; click **Authorize Action** to confirm it
- `what's our refund policy for orders over 30 days old?` — a cited policy answer pulled from the seeded knowledge base
- `how many agents are online right now` — live queue availability
- `issue a $10 account credit for ticket TCK-xxxx for a shipping delay` — small amounts auto-approve on creation; try a larger amount to see it land in the Escalation Queue instead (team-lead login required to approve/reject it there)
- `can you create a ticket for me, customer is Sofiya Reyes, she can't reset her password` — proposes a new ticket
- try a real multi-turn exchange: `I want to raise an escalation`, then, once it asks what for, reply with just `refund of $75 for ticket TCK-xxxx` — the second message is understood using the first, not treated as a standalone request

## Testing

```bash
cd backend
uv run pytest
```

Runs fully offline — no Gemini key or network access needed. The suite covers deterministic logic only (SQL-security allow-list, entity resolution, circuit breaker, CRUD, the signed-token propose→confirm flow, analytics aggregation), never live LLM classification. Each run gets its own throwaway SQLite DB and Chroma directory — your real `customer_ops.db` is never touched.

The frontend has no automated test suite; `npm run build` (which runs `tsc -b` first) is the closest thing to a regression check.

## Deployment

Verified working end-to-end on a fully free stack: **Render** (backend) + **Neon** (Postgres) + **Vercel** (frontend).

- **Database** — create a free [Neon](https://neon.tech) Postgres project and use its **pooled** connection string (the one with `-pooler` in the hostname) as `DATABASE_URL` — Neon's free tier suspends its compute after a few minutes idle, and the pooler absorbs that reconnect churn far more reliably than a direct connection. `psycopg2-binary` is already a backend dependency, so no code changes are needed to point at Postgres instead of SQLite. Seed it once: `DATABASE_URL="<neon connection string>" uv run python -m data.seed_data`.
- **Backend (Render)** — `backend/requirements.txt` is a pinned, production-only export of the `uv` lockfile (regenerate with `uv export --no-dev --no-hashes --format requirements-txt -o requirements.txt` after changing dependencies). New Web Service, root directory `backend`, build command `pip install uv && uv sync --frozen`, start command `uv run uvicorn app.main:app --host 0.0.0.0 --port $PORT`. Set `DATABASE_URL` (above), `GEMINI_API_KEY`, `JWT_SECRET_KEY`, `DEBUG=false`, and `CORS_ORIGINS` to your deployed Vercel URL as environment variables. The Chroma vector store does **not** need persistent disk — it lives on Render's ephemeral local disk and is transparently rebuilt from the `kb_documents` table on every boot if empty (`rag_service.reingest_if_empty`, called from the app's lifespan), so a free instance with no attached disk is enough.
- **Keep it warm, for free** — a free web service spins down after 15 minutes idle, and Neon's free compute similarly suspends. `GET /health` checks both server and DB liveness (`SELECT 1`) and needs no auth; point a free external pinger (e.g. [cron-job.org](https://cron-job.org)) at it on a ~10 minute interval to keep both from ever idling out. `GET /` is a separate, DB-free liveness check, suitable as the host's own configured health-check path.
- **Frontend (Vercel)** — a standard Vite project, auto-detected; root directory `frontend`, no build command changes needed. Set `VITE_API_BASE_URL` to the deployed Render URL + `/api/v1` as an environment variable, then once both are live, update the backend's `CORS_ORIGINS` to the real Vercel URL and let Render redeploy.
